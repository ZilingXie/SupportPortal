1）知识入库与数据清洗模块

你要实现什么

把官网文档、内部技术文档、后续工单沉淀文档，统一变成可入库的标准知识单元。

实现方式

先做一层 ingestion pipeline：
	1.	文档拉取
	•	输入源：官网 MD 文档、内部技术文档、n8n 总结出的工单文档
	2.	文档标准化
	•	去掉无关 header/footer
	•	统一编码、空行、标题层级
	•	给每篇文档补 metadata：doc_id / source / title / url / updated_at / product / language
	3.	分块前预处理
	•	保留标题结构
	•	提取段落、表格、代码块边界
	4.	输出结构
	•	形成统一 JSON 结构，便于后续切块和入库

为什么这是第一步

你朋友专门提到，RAG 项目第一点就要能讲清楚“原始数据是什么，怎么处理，怎么入库”。 ￼

做到什么算完成

	•	每篇文档有哪些 metadata
	•	入库前做了哪些清洗
	•	哪些源会自动热更新

2）chunk 切分策略升级

你要实现什么

把你现在“按 Markdown 标题切”的方式，升级成固定 token 长度 + 标题协同的切分策略。

实现方式

做两套切分器：

方案 A：你当前版本
	•	按 Markdown # / ## / ### 切

方案 B：建议主用版本
	•	以标题为语义锚点
	•	再按固定 token 窗口切分，比如：
	•	chunk_size = 500
	•	overlap = 80~120
	•	如果 chunk 末尾离下一个标题太近，就扩展或收缩，避免出现过短的“长尾碎片 chunk”

你朋友对这个点讲得很明确：
只按标题切会导致 chunk 长短不均，很多特别小的 chunk 很难召回；更好的办法是固定 token 长度，再结合标题做边界修正。

建议你直接做的实验

至少对比这 3 组：
	•	300 tokens
	•	500 tokens
	•	800 tokens

然后用同一批测试问题去比较召回命中和回答质量。你朋友也明确建议你做这种“小型消融实验”。 ￼

做到什么算完成

你能回答：
	•	为什么选这个 chunk size
	•	为什么不用纯标题切
	•	overlap 设多少
	•	实验结果提升了什么

4）向量检索 + BM25 混合召回

你要实现什么

从单路向量检索升级成多路召回。

实现方式

至少做这两路：

第一路：向量召回

	•	top_k_vector = 20

第二路：BM25 / 关键词召回
可选两种实现：
	•	轻量版：PostgreSQL Full Text Search
	•	标准版：Elasticsearch / OpenSearch

朋友这里的建议很明确：

融合方式

	•	合并候选集
	•	用 RRF 做排序融合

做到什么算完成

5）意图识别与分流模块

你要实现什么

不要让所有问题都走检索链路。

实现方式

先用最简单、最好落地的版本：Prompt 分类器。

你朋友其实已经把话说透了：
意图识别一开始不用搞复杂模型，先用 prompt 做分类就够了。

建议分类

至少分成这几类：
	1.	chitchat
	•	你好、谢谢、今天天气怎么样
	•	直接让模型回答，不走检索
	2.	unsafe_or_reject
	•	敏感、违规、无关内容
	•	直接拒答
	3.	retrieval_qa
	•	产品使用、排障、配置、文档问答
	•	走 RAG
	4.	clarification_needed
	•	问题模糊、信息不全
	•	先反问补充信息
	5.	human_handoff
	•	高情绪、高风险、工单升级类
	•	直接触发人工接管或优先队列

推荐实现

做一个 intent_router：
	•	输入：用户 query + 上下文
	•	输出：
	•	intent
	•	confidence
	•	next_action

做到什么算完成

你能展示：
	•	“你好”不会再走检索
	•	明显违规问题会拒答
	•	模糊问题会先澄清
	•	高风险问题可以直转人工

6）Rerank 重排模块

你要实现什么

多路召回之后，不直接喂给大模型，先做一次 relevance 重排。

实现方式

流程：
	1.	向量召回 top20
	2.	BM25 召回 top20
	3.	RRF 融合后得到 top30
	4.	用 reranker 排序
	5.	取最终 top5~8 给生成模型

你朋友说得非常明确：
一个完整的常规 RAG 链路，应该有检索前处理、检索中融合、检索后 rerank。

做到什么算完成

你能回答：
	•	为什么融合后还要 rerank
	•	最终喂给模型的不是召回结果，而是重排后的结果
	•	rerank 后回答逻辑性和引用准确率有没有提升

7）回答生成与引用约束

你要实现什么

让模型回答时必须“基于召回证据”，并输出结构化结果。

实现方式

让生成模型输出固定 schema，比如：

{
  "answer": "...",
  "citations": [
    {"doc_id": "...", "chunk_id": "...", "source": "..."}

  "confidence": 0.82,
  "needs_human": false

Prompt 约束：
	•	只能使用提供的上下文回答
	•	没有证据就明确说不知道
	•	输出引用 chunk id / source
	•	不允许编造链接

这个点正好能补你上次正式面试里“链接有时候会错”的问题。 ￼

做到什么算完成

你能展示：
	•	回答附带引用
	•	没命中时不乱答
	•	高风险或低置信度时触发人工

8）Query 改写 / Multi-query

你要实现什么

把用户模糊、不完整的问题，改写成更适合检索的查询。

实现方式

先做两层：

层 1：单 query rewrite
	•	用大模型把原问题改写成更明确、可检索的 query

层 2：multi-query
	•	把一个复杂问题拆成 2~4 个子 query
	•	每个 query 分别走召回
	•	结果汇总、去重、截 top_k

这就是你朋友建议你加在检索前的增强模块。

做到什么算完成

你能回答：
	•	哪些问题适合 query rewrite
	•	哪些问题适合 multi-query
	•	加入后召回覆盖率是否更高
