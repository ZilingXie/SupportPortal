# SupportPortal RAG 重构规划

## 一、文档目标

这份文档用于整理 `SupportPortal` 的 RAG 重构路线，目标不是从零重做一个新系统，而是在当前已经具备的工单系统、异步 worker、`pgvector` 检索、引用展示和人工接管能力之上，把现有方案升级为一个更完整、更容易评估、也更方便对外讲述的 RAG 系统。

这份规划默认服务两个场景：

1. 作为后续开发的阶段性路线图。
2. 作为项目汇报或面试时介绍系统演进思路的依据。

## 二、总原则

先把常规 RAG baseline 做完整，再考虑更重的增强路线。

这意味着当前阶段优先补齐以下主线：

1. 数据处理与标准化入库
2. 更合理的 chunk 切分
3. 可切换的 embedding
4. 向量检索与关键词检索的混合召回
5. rerank 重排
6. 意图识别与分流
7. 带引用、可约束的回答生成
8. benchmark 与持续评估

在这条主线完整且稳定之前，不优先引入 `GraphRAG`、`Neo4j`、复杂 agentic workflow 或重型图检索方案。

## 三、当前基线

结合当前仓库实现，`SupportPortal` 已经具备以下基础：

1. 已有基于 `pgvector` 的向量检索问答链路，核心逻辑集中在 `backend/services/rag_qa.py`。
2. 当前回答链路已经支持基础 citation 输出，前端和工程师端都能消费 `chunk_id / source_path / source_url / heading` 这套结构。
3. 已有完整的工单主流程，包括客户提问、AI 回复、工程师接管、状态同步和事件记录。
4. 已有 Redis 任务队列和 worker，可承接异步 AI 查询任务。
5. 已有人工接管与工程师跟进逻辑，说明系统已经具备“低置信度转人工”的落点。

同时，当前基线也存在明显缺口：

1. 还没有标准化的知识入库流水线，知识来源、清洗规则和 metadata 结构还未系统化。
2. 还没有正式的 hybrid retrieval，当前更接近“向量召回为主，关键词补救为辅”。
3. 还没有独立的 rerank 模块。
4. 还没有正式的 benchmark 和消融实验体系，难以量化改动是否有效。
5. 还没有完整的热更新入库链路，尤其缺少面向工单沉淀知识的标准入口。
6. 还没有独立的意图识别与 query rewrite 模块，所有问题尚未形成稳定分流策略。

## 四、阶段规划

### P0：先补齐完整 RAG baseline

#### 1. 知识入库与数据清洗模块

**要实现什么**

把官网文档、内部技术文档、以及后续由工单总结得到的知识内容，统一转换成可以稳定入库的标准知识单元。

**为什么现在做**

如果无法说明原始数据来自哪里、如何清洗、如何入库，那么后续 chunk、embedding、召回和评估都缺少统一基线，系统也很难工程化。

**建议实现方式**

1. 建立统一 ingestion pipeline。
2. 输入源默认包括：
   - 官网或产品文档
   - 内部技术文档
   - n8n 汇总后的工单知识文档
3. 统一做文本标准化：
   - 去掉无关 header/footer
   - 统一编码、空行和标题层级
   - 抽取表格、代码块、段落边界
4. 为每篇文档补齐 metadata：
   - `doc_id`
   - `source`
   - `title`
   - `url`
   - `updated_at`
   - `product`
   - `language`
5. 标准化输出建议统一为 JSON 文档结构，作为后续 chunk 和索引的上游输入。

**完成标准**

做到以下几点就算这一模块完成：

1. 能说清楚当前支持哪些知识源。
2. 能列清每篇文档写入了哪些 metadata。
3. 能说明入库前做了哪些清洗。
4. 能说明哪些来源支持自动热更新，哪些仍是手动导入。

#### 2. Chunk 切分策略升级

**要实现什么**

把当前偏简单的切分方式升级为“固定 token 长度 + 标题协同”的 chunk 策略。

**为什么现在做**

纯标题切分容易导致 chunk 长度极不均衡，过短 chunk 不利于召回，过长 chunk 又会降低上下文利用率。

**建议实现方式**

1. 保留当前基于 Markdown 标题切分的方式，作为对照组。
2. 主方案改为：
   - 以标题作为语义锚点
   - 以固定 token 窗口做主体切分
   - 在标题边界附近做适度扩展或收缩，避免产生很短的尾部碎片
3. 至少比较以下三组参数：
   - `chunk_size = 300`
   - `chunk_size = 500`
   - `chunk_size = 800`
4. overlap 建议从 `80 ~ 120` 开始实验。

**完成标准**

1. 能解释为什么最终选择某个 chunk size。
2. 能解释为什么不再使用纯标题切分。
3. 能说明 overlap 的选择依据。
4. 能用统一测试集展示切分优化后的召回或回答质量变化。

#### 3. Embedding 选型与可切换入库

**要实现什么**

把 embedding 从“单一能跑模型”升级为“可比较、可切换、可记录”的方案。

**为什么现在做**

embedding 是召回质量的核心因素之一，如果后续想系统比较中文效果、升级模型或做消融实验，必须先把 provider 抽象做好。

**建议实现方式**

1. 设计统一的 provider 抽象层，方向上可包含：
   - `EmbeddingProvider`
   - `embed_documents()`
   - `embed_query()`
2. 初期只需要把方向写清，不在这份文档里展开代码实现。
3. 推荐对比路径：
   - 当前 OpenAI embedding 作为 baseline
   - 新增一个中文表现更好的 embedding 作为候选
4. 写入向量库时建议同时记录：
   - `chunk_id`
   - `doc_id`
   - `chunk_index`
   - `embedding_model`
   - `text`
   - `metadata`

**完成标准**

1. 能回答为什么保留当前模型作为 baseline。
2. 能说明新增 embedding 的预期优势。
3. 能比较不同模型在中文文档上的召回表现。
4. 更换模型后能量化是否真的带来提升。

#### 4. 向量检索 + PostgreSQL FTS 混合召回

**要实现什么**

把单路向量检索升级为双路混合召回。

**为什么现在做**

向量检索擅长语义相似，但对精确关键词、数字约束、产品名、报错码等内容不够稳。关键词检索可以补足这部分短板。

**建议实现方式**

1. 第一阶段默认方案使用 PostgreSQL Full Text Search，不引入 OpenSearch。
2. 保留 `pgvector` 语义召回。
3. 增加 PostgreSQL FTS 作为 BM25/关键词召回的轻量替代。
4. 两路分别召回候选后，使用 `RRF` 做融合排序。
5. 初始建议：
   - 向量召回 `top_k = 20`
   - FTS 召回 `top_k = 20`
   - 融合后保留 `top_k = 30`

**完成标准**

1. 能解释为什么向量检索单独使用不够。
2. 能说明 FTS 补足了哪些场景。
3. 能清楚讲出两路候选如何融合。
4. 能展示相对单路检索的命中率变化。

#### 5. 意图识别与分流模块

**要实现什么**

避免所有问题都无差别进入检索链路。

**为什么现在做**

RAG 更适合文档问答，不适合闲聊、违规内容或明显需要澄清的问题。如果没有分流，系统会产生不必要延迟，也更容易误答。

**建议实现方式**

1. 第一阶段采用 prompt 分类器即可。
2. 建议至少分为以下几类：
   - `chitchat`
   - `unsafe_or_reject`
   - `retrieval_qa`
   - `clarification_needed`
   - `human_handoff`
3. 推荐后续方向上增加：
   - `intent_router`
   - 输出 `intent / confidence / next_action`

**完成标准**

1. 闲聊问题不再进入检索。
2. 明显违规问题会拒答。
3. 模糊问题会先追问。
4. 高风险或高情绪问题可直接转人工。

#### 6. Rerank 重排模块

**要实现什么**

在多路召回之后，增加 relevance 重排，而不是把候选直接喂给生成模型。

**为什么现在做**

融合后的候选集覆盖更大，但排序未必足够精确。重排能进一步提升最终喂给大模型上下文的相关性。

**建议实现方式**

推荐后续链路顺序如下：

1. 向量召回 `top20`
2. FTS 召回 `top20`
3. RRF 融合得到 `top30`
4. rerank 重排
5. 取最终 `top5 ~ top8` 提供给生成模型

**完成标准**

1. 能解释为什么融合后仍然需要 rerank。
2. 能说明最终上下文不是原始召回，而是重排后的结果。
3. 能通过 benchmark 展示回答逻辑性或引用准确率是否提升。

#### 7. 回答生成与引用约束

**要实现什么**

让模型必须基于召回证据作答，并保持结构化输出。

**为什么现在做**

如果回答不受证据约束，citation 就会失去意义，也无法稳定判断幻觉率和转人工时机。

**建议实现方式**

1. 生成模型统一输出结构化结果，方向上建议包含：
   - `answer`
   - `citations`
   - `confidence`
   - `needs_human`
2. Prompt 约束需要明确：
   - 只能依据上下文作答
   - 没有证据时明确说不知道
   - 输出引用的 chunk 或来源标识
   - 不编造链接
3. 继续保持当前前端已消费的 citation 结构兼容。

**完成标准**

1. 回答附带引用。
2. 没命中时不会乱答。
3. 低置信度或高风险情况可触发人工接管。

### P1：在 baseline 跑顺后做增强

#### 8. Query Rewrite / Multi-query

**要实现什么**

把模糊问题改写成更适合检索的查询，必要时把复杂问题拆成多个子查询。

**为什么现在做**

不少检索失败不是因为知识库没有答案，而是因为原始问题表达过于模糊、口语化或复合。

**建议实现方式**

1. 先做单 query rewrite。
2. 再做 multi-query。
3. multi-query 建议控制在 `2 ~ 4` 个子查询。
4. 各路结果统一汇总、去重，再进入融合和重排。

**完成标准**

1. 能区分哪些问题适合 rewrite。
2. 能区分哪些问题适合 multi-query。
3. 能展示召回覆盖率是否提升。

#### 9. 知识库热更新

**要实现什么**

把关闭工单后的经验沉淀成知识，并能较快进入在线检索。

**为什么现在做**

只有把工单经验沉淀进知识库，RAG 才能形成反馈闭环，而不是静态 FAQ。

**建议实现方式**

1. 把 n8n 视为外部系统，不在这份文档里展开节点级设计。
2. 对仓库侧只定义标准对接入口，例如：
   - `POST /api/internal/knowledge/hot-update`
3. 推荐热更新路径：
   - 工单关闭
   - n8n 脱敏
   - n8n 生成总结文档
   - 调用仓库内热更新接口
   - 进入标准化、chunk、embedding、索引刷新流程
4. 去重策略建议放在文档级和离线重建阶段，不在每次入库时做重型全量相似去重。

**完成标准**

1. 能说明新工单如何进入知识库。
2. 能说明热更新多快生效。
3. 能清楚解释去重策略放在哪一层。

#### 10. Benchmark 与评估模块

**要实现什么**

建立一套可重复的评估机制，用来判断系统改动是否真的有效。

**为什么现在做**

如果没有统一测试集和指标，后续所有优化都只能靠主观感觉，很难证明系统是否提升。

**建议实现方式**

1. 构造测试集：
   - 先从文档中生成 QA 对
   - 允许模型辅助生成
   - 再经过 refine、交叉检查或人工抽样确认
2. 至少评估以下指标：
   - `answer_accuracy`
   - `citation_correctness`
   - `retrieval_recall@k`
   - `hallucination_rate`
   - `answer_logic_score`
3. 每次只改一个变量，并复用同一套 benchmark。

**完成标准**

1. 能输出一张统一对比表。
2. 能回答每个优化动作带来了什么变化。
3. 后续优化不再依赖主观感受，而是能回到同一套评测框架中比较。

### P2：有时间再做的升级项

#### 11. HyDE 检索一路

**要实现什么**

增加一条“由模型先生成假设答案，再拿假设答案去检索”的增强召回路径。

**为什么现在做**

HyDE 适合补强部分语义表达不稳定的问题，但它应建立在现有主链路已经稳定的基础上。

**建议实现方式**

1. 用户 query
2. LLM 生成一段假设文档
3. 对假设文档做 embedding
4. 再用其参与向量召回

**完成标准**

1. HyDE 只在 baseline 稳定后接入。
2. 能证明它优于现有主链路，否则不默认启用。

#### 12. 轻量 Graph 检索

**要实现什么**

不是直接上重型 GraphRAG，而是做一版轻量图增强检索。

**为什么现在做**

图增强更适合在普通 RAG 已经完整后，作为额外召回能力，而不是当前阶段的主线。

**建议实现方式**

1. 文档中抽取实体、关系、三元组。
2. 单独维护轻量 graph store。
3. 在检索时把 graph 作为附加召回链路，而不是替代主链路。

**完成标准**

1. 图增强是加分项而不是依赖项。
2. 不影响原有常规 RAG 主流程。

#### 13. Agentic 工具路由

**要实现什么**

把若干检索与处理模块封装成工具，由模型在更高层进行选择。

**为什么现在做**

这部分展示性很强，但成本高、延迟高，且容易引入流程冲突，因此必须放在最后。

**建议实现方式**

按阶段开放能力：

1. 阶段一：只允许选择直接回答、意图识别、query rewrite。
2. 阶段二：允许选择 embedding 检索、FTS 检索、HyDE 检索、graph 检索。
3. 阶段三：允许决定是否 rerank、是否人工接管。

**完成标准**

1. agentic 路由不会破坏已有主链路。
2. 能说明性能代价和收益。
3. 只在前面模块都已有稳定实现后再启动。

## 六、建议实验矩阵与评估方式

### 核心评估项

1. `answer_accuracy`
2. `citation_correctness`
3. `retrieval_recall@k`
4. `hallucination_rate`
5. `answer_logic_score`

### 建议实验矩阵

| 变量 | 对照项 |
| --- | --- |
| chunk size | `300 / 500 / 800` |
| embedding | 当前 OpenAI baseline vs 新中文 embedding |
| retrieval | 向量 only vs 向量 + FTS |
| rerank | 无 vs 有 |
| rewrite | 无 vs 有 |

### 评估原则

1. 每次只改一个变量。
2. 所有实验复用同一批测试问题。
3. 所有结论尽量回到统一表格中比较。
4. 如果某个增强没有稳定带来提升，就不默认进入主链路。

## 七、推荐开发顺序

### 第 1 阶段

1. ingestion 标准化
2. chunk 策略升级
3. embedding provider 抽象
4. benchmark baseline

### 第 2 阶段

1. PostgreSQL FTS
2. RRF 融合
3. rerank
4. 结构化回答与引用约束

### 第 3 阶段

1. intent router
2. query rewrite
3. multi-query
4. 热更新链路接入

### 第 4 阶段

1. HyDE
2. 轻量 graph
3. agentic routing

## 八、最终可讲的系统架构

当 P0 和 P1 完成后，整个系统可以按四层来讲述：

### 1. 数据层

负责官网文档、内部文档和历史工单知识的标准化、切分和入库。

### 2. 检索层

负责向量召回、PostgreSQL FTS、RRF 融合和 rerank。

### 3. 生成层

负责基于证据的回答生成、引用输出、低置信度拒答和转人工。

### 4. 评估与反馈层

负责 benchmark、指标对比、实验记录和知识库热更新。

## 九、阶段完成定义

| 阶段 | 完成定义 |
| --- | --- |
| P0 | 能说明知识从哪里来、如何清洗、如何切分、如何召回、如何重排、如何基于证据回答，并能展示引用与转人工逻辑 |
| P1 | 能展示 rewrite、多 query、热更新和 benchmark 表格，并能量化每一步优化的收益 |
| P2 | 能把 HyDE、轻量 graph、agentic routing 作为增量升级项说明，但不影响常规 RAG 主流程 |

## 十、默认假设

1. 本文档只整理规划，不包含代码 patch、数据库 migration 细节或前后端文件级改造清单。
2. 混合召回第一阶段默认写 PostgreSQL FTS，不把 OpenSearch 作为主方案。
3. n8n 作为外部系统对接说明，不展开 n8n 节点内部细节。
4. 不复用 `docs/SUPPORTPORTAL_AI_OPTIMIZATION_PLAN.md` 的结构，单独保留一份更聚焦 RAG 重构的规划文档。
5. 当前阶段目标是先把 SupportPortal 的常规 RAG 主链路做完整，再考虑更重的图增强和 agent 化方案。
