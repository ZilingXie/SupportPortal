当前判断

Billing 是最接近可试运行的确定性闭环；Assignment 仍是独立 demo；Engineer Multi-Agent 已有后端契约骨架和中文主线计划，但真实生命周期仍未接管；RAG/KG 已完成 cusmem 产品化整理，下一步才是 SupportPortal adapter 与评测。

  • QBR 可以把 Billing 作为最强 demo，但必须把 Zendesk、幂等和人工审核标为试运行前置条件。
  • Assignment 和 Multi-Agent 都要避免过度承诺：前者是 localStorage 原型，后者是 skeleton + plan，还不是生产主链路。
  • RAG/KG 适合讲架构方向和边界，不能把 vendored cusmem 等同于已上线的 KG 检索能力。

    建议 QBR 路线

    如果要汇报或继续推进，建议按风险递增顺序讲：先 POC/原型，再线上闭环，再知识架构。

    1. Billing

    展示确定性最强的白名单自动化：字段收集、route、ticket 持久化、邮件升级、历史查询，以及对外 `TK-...` ticket id 统一已经闭环，下一步是 Zendesk、幂等和试运行质量复盘。

    2. Assignment

    展示工程师排班/单工单/SLA 的体验原型，明确它目前是 demo，不是生产调度器；下一步补数据模型、审计事件和真实队列。

    3. Multi-Agent

    展示 Engineer AI 从 guardrail-only 走向 multi-agent 主链路的骨架、安全边界和中文实施计划；当前下一步是任务 2：先把真实 Plan Agent 接进生命周期，再继续补 Memory Review/Implement/Conclude。

    4. RAG vs KG

    把知识边界讲清楚：文档和 citation 留在 RAG，确认案例和经验进入 Case Memory/KG；cusmem 已产品化整理，下一步才是 SupportPortal adapter、schema source 和对照评测。
