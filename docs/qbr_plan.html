    Engineer AI Agent 架构

    这张 Mermaid 图固定当前讨论后的 multi-agent 生命周期：client escalation 先被总结成可审计 packet，再进入 AI 调查循环，最后由工程师和 guardrail 共同完成客户回复。

    Summary → Plan → Execute → Review → Guardrail

    当前只是计划与契约方向，不代表线上 runtime 已接管；mem0 和 skill list 尚未完成时，Plan Agent 必须使用 deterministic fallback。

    flowchart TD
  C["Client AI handle 不了客户问题"] --> E["Escalate to Engineer"]
  E --> S["Summary Agent: 整理上下文、线索、缺失信息和 redaction boundary"]
  S --> T["Create Engineer Ticket with summary packet"]
  T --> P["Plan Agent: summary packet + mem0 + skill list / fallback"]
  P --> X["Execute Agent: 调度 allowlisted subagents"]
  X --> G["Evidence packet + task results"]
  G --> R["Review Agent: 判断下一步"]
  R -->|ready_for_engineer| F["告诉工程师发现"]
  R -->|replan_required, max 2 retries| P
  R -->|unable_to_resolve| U["告诉工程师目前信息无法回答或解决"]
  F --> H["Engineer 操作"]
  U --> H
  H -->|revise| P
  H -->|approve| Q["Guardrail: 生成或校验 customer-facing reply"]
  Q --> A["Engineer final approve"]
  A --> Y["回复客户"]
  Y --> Z["关闭 Engineer 工单"]
  Z --> M["写 audit event + Case Memory candidate"]

    Review Agent 的三种决策是 ready_for_engineer、replan_required、unable_to_resolve；关闭工单后只写 Case Memory candidate，不自动晋升 active memory。

    建议 QBR 路线

    如果要汇报或继续推进，建议按风险递增顺序讲：先 POC/原型，再线上闭环，再知识架构。

    1. Billing

    展示确定性最强的白名单路由闭环：`/account` case 持久化、route、单一 `TK-...` ticket id、automation 状态记录和历史查询已经闭环；当前不执行自动化动作，下一步是 Zendesk、幂等和人工审核试运行。

    2. Assignment

    展示工程师排班/单工单/SLA 的体验原型，明确它目前是 demo，不是生产调度器；下一步补数据模型、审计事件和真实队列。

    3. Multi-Agent

    展示 Engineer AI 从 guardrail-only 走向 Summary Agent、Plan Agent、Execute Agent、Review Agent 的调查主链路；当前下一步是先实现 Summary Agent 和 summary packet，再把 Plan Agent 接入 mem0/skill fallback。

    4. RAG vs KG

    把知识边界讲清楚：文档和 citation 留在 RAG，确认案例和经验进入 Case Memory/KG；cusmem 已产品化整理，下一步才是 SupportPortal adapter、schema source 和对照评测。
