# SupportPortal POC 结果汇报

> 快照日期：2026-04-05

## 一句话结论

SupportPortal 这次 POC 可以定义为**部分通过**：核心方向已经被验证，建议进入下一阶段继续投入；但当前还不具备直接生产上线的条件。换句话说，这次 POC 证明了“这条路值得走”，但还没有证明“现在就能大规模上线”。现在不能上线的原因，主要是稳定性、性能和运行保障还没有补齐，这不代表 POC 失败，而是说明项目已经从“是否可行”进入“如何可控落地”的阶段。

## 为什么值得做

我们做这个 POC，不是为了验证单点 AI 能不能回答问题，而是为了验证一个更有业务价值的模式：能不能把常见支持问题先交给系统处理，把复杂问题及时转给工程师，让支持效率、响应速度和处理一致性都明显提升，同时让管理层能看见整个处理过程，而不是继续完全依赖人工经验驱动。

- 如果这条模式成立，客户常见问题可以更快得到响应，人工资源可以集中处理真正复杂的问题。
- 如果这条模式成立，支持质量会更稳定，减少“同类问题不同人处理结果差异很大”的情况。
- 如果这条模式成立，后续就有机会把支持流程做成可管理、可衡量、可持续优化的系统，而不是继续靠人堆。

## 本次验证结果

1. **核心业务闭环已经成立。**
   客户提问、系统初步判断、自动处理、复杂问题转人工、工程师接手处理、管理端追踪，这条主链路已经打通。业务意义是：这个项目已经不是概念演示，而是形成了可以继续打磨的业务流程雏形。

2. **“AI 先处理，复杂问题转人工”的模式已经被验证。**
   系统已经能先处理一部分标准化问题，遇到证据不足或复杂场景时再交给工程师，而不是让 AI 硬答。业务意义是：可以同时争取效率和风险控制，不会因为追求自动化而失去服务质量。

3. **工程师协同处理机制已经成立。**
   工程师不是被动兜底，而是能在系统内接手、审核、跟进和回传结果。业务意义是：后续这套体系可以沉淀成标准 support 流程，而不是临时补救动作。

4. **下一阶段继续投入是有基础的。**
   管理端看板、运行追踪和部署基础已经具备，说明后续不是从零开始重做，而是在已有闭环上补性能、稳定性和管理能力。业务意义是：继续投入的产出路径比较清晰，风险也相对可控。

## 当前风险与边界

1. **还没有生产级性能和稳定性基线。**
   目前已经证明“能跑通”，但还没有证明“在真实业务量下能稳定跑”。这也是为什么现在不建议直接上线。

2. **还没有完整的监控告警和故障应对能力。**
   当前系统具备继续验证的基础，但还不具备成熟产品应有的运行保障能力。一旦进入真实环境，发现问题、定位问题、快速恢复的能力还需要补齐。

3. **真实复杂场景能力还不完整。**
   例如附件输入、更顺滑的交互体验等高频真实使用场景还没有补全。这不影响 POC 对核心模式的验证结论，但会影响后续试运行阶段的实际体验。

## 下一阶段建议与需要支持

### 下一阶段建议

建议下一阶段的目标从“证明可行”切换到“准备试运行”。重点不是继续讲方案，而是补齐三件事：第一，建立性能和稳定性基线；第二，补齐监控告警和运行保障；第三，把关键体验缺口补到可试运行水平。只有完成这一步，才能决定是否进入更真实的业务验证或小范围上线。

### 需要支持

建议给项目预留一轮 **2-4 周** 的连续投入窗口，重点支持以下资源：

- 稳定的测试/试运行环境，用来做性能、稳定性和流程验证。
- 必要的模型与服务器预算，用来支撑持续验证，而不是只做一次性演示。
- 测试和运维配合，帮助补齐压测、监控、告警和发布保障。
- 管理层对下一阶段目标的统一口径：当前目标是做成“可试运行”，不是直接追求“立即上线”。

### 建议老板拍板的事项

建议老板本次明确批准三件事：

1. 批准项目进入下一阶段，继续做试运行前准备，而不是停留在 POC 演示阶段。
2. 批准“当前版本不直接上线”的前提，避免团队在基础能力未补齐前被迫承担生产风险。
3. 批准下一阶段所需的时间窗口和基础资源，包括测试环境、必要预算，以及测试/运维支持。
