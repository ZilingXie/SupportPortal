SupportPortal Phase 1

从 Zendesk 平替，走向 AI-native Support System

这不是一次工具替换，而是把路由、质量检查、调查辅助和管理指标内建到 support 流程里。Phase 1 的目标是先证明系统可控、可审计、可小流量试运行。

  • 0:35 架构与角色变化
  • 1:05 AgentRelay foundation
  • 1:40 Guardrail showcase
  • 2:25 Dashboard 与路线图
批注：演示时这么说

“今天我不把它包装成一个 ticket UI。Phase 1 要证明的是：我们能把 support 的质量检查、调查协作和管理指标放进系统流程里，而不是继续依赖 Zendesk 加人工经验。”

批注：准备建议

这一页控制在 15 秒以内。不要展开所有功能，先立住主线：不是 SaaS 平替，而是 AI-native support operating system。

01 · Why now

传统 SaaS 已经很难承接我们的 support 目标。

Zendesk license 续费约 73k USD/year，但更大的问题不是价格，而是团队需要更深的流程、数据和质量控制能力。

批注：演示时这么说

“痛点不是单点功能缺失，而是 SLA、回复质量、billing 自动化和交接 gap 都散在不同工具里。Zendesk 可以记录工单，但它不能按我们的规则实时判断这条回复能不能发。”

批注：准备建议

准备一个具体例子：例如 billing case 中哪些不需要 HITL、哪些必须人工 approve。领导会更容易判断 POC 切入点是否安全。

SLA 回复不及时、升级等待和交接空档，都不能只靠事后报表管理。
73k 年费只买到通用 SaaS 能力，关键流程仍需要外部脚本、人工判断和临时补丁。
Billing 部分 invoice、account fraud / deactivate 等 case 不需要完整 HITL 流程，适合先做受控自动化 POC。
02 · Big picture

Phase 1 先不改变客户入口，只改变内部处理能力。

客户仍然从 Zendesk 进入；内部通过 Zendesk webhook / N8n 转到 SupportPortal，先跑 shadow mode、真实 case replay 和 1% 小流量门禁。AgentRelay 已补上后续跨 Agent 协作所需的通信基础。

批注：演示时这么说

“这里的迁移策略很保守：客户入口不动，CX 体验不变。我们先把内部 routing、review、guardrail 和 agent 协作跑起来，证明可控之后再扩大流量。”

03 · Agent-to-Agent Foundation

AgentRelay 让 SupportPortal 从单 Agent 工作台，升级为可协作的 Agent network。

复杂 case 的瓶颈不是生成一句回复，而是跨系统、跨角色拿到可信证据。AgentRelay 已完成 A2A-shaped relay、MCP tools、token auth、thread reuse、completion ownership 和 audit events，为后续 Billing / Log / R&D / Data Agent 接入打基础。

批注：演示时这么说

“AgentRelay 的价值是把 Agent 之间的协作从临时聊天变成任务状态机。谁创建任务、谁 claim、交付了什么 artifact、结果有没有回到原始 thread，都能审计。”

批注：图片建议

这页建议准备 AgentRelay event trace 截图。不要只展示 GitHub repo 首页；要展示 task.created -> artifact.submitted -> reply.delivered 这条链路，证明它已经可以承接跨 Agent 交付。

Image needed · AgentRelay task trace 建议放 task event trace 截图：task.created -> task.claimed -> thread.created -> artifact.submitted -> ownership.transferred -> reply.delivered -> task.completed。重点证明它是可审计状态机，不是黑盒聊天。
Thread reuse 结果必须投递回原始 requester_thread_id，避免新建散乱线程；Support 场景里就是回到原始 case thread。

04 · Role shift

AI 不是替代 support engineer，而是把 manager 的日常质量检查产品化。

客户侧体验暂时不变；工程师从重复流程中释放出来；AI agent 承担实时检查、辅助调查和跨系统协作。

批注：演示时这么说

“很多人担心 AI 替代员工，但我认为第一阶段更准确地说是替代 manager 的 day-to-day 检查动作：技术是否准确、有没有下一步、有没有 SLA 风险、客户情绪是否异常。”

批注：准备建议

这里语气要克制：不要说 manager 不重要，而是说 manager 从逐条检查低级错误，转向规则设计、例外处理和质量抽查。

Before

  • Manager 只能抽样 review，无法逐条检查技术细节、表达边界和 SLA 风险。
  • 客户不满通常要等客诉后才暴露，情绪和交接风险发现太晚。
  • 工程师反复 copy/paste 到外部 AI，过程不可审计、不可稳定复用。

After

  • 每次回复都先过 AI guardrail，低级错误在发送前被拦住。
  • 每条客户信息都可以做情感检测和 SLA 风险识别，提前报警。
  • Support Agent 可通过 AgentRelay 调度 Billing、日志、研发、数据 Agent 收集证据，再由人和 guardrail 控制客户可见输出。
05 · Showcase

演示重点：AgentRelay 先组织拿证据，AI 再拒绝不完整回复。

这个 case 最能说明项目价值：系统不是急着替人回答，而是先把调查任务交给专用 Agent，再在客户看到之前拦住缺 conclusion、proof 和 next step 的回复。

批注：演示时这么说

“这个 demo 我会故意给一个很像真实场景的低质量回复。系统不是直接改写得更礼貌，而是先问：证据够不够？结论清不清楚？客户下一步是什么？”

06 · Dashboard

管理指标也要从 SLA 时代升级到 AI guardrail 时代。

传统指标仍然重要，但 Phase 1 开始追踪 AI 是否真的降低风险、提升质量，并解释为什么某些 case 还不能自动化。

批注：演示时这么说

“以前的管理指标主要是 response time 和 SLA。现在还要看 AI guardrail pass rate、拒绝原因、not automated reason、AgentRelay delivery success rate。这样我们知道 AI 是在降风险，还是只是更快地产生风险。”

批注：准备建议

如果时间不够，这页只讲两个指标：guardrail pass/reject reason 和 A2A delivery success。它们最能说明 Phase 1 的管理价值。

  • 传统指标：first response time、second response time、SLA risk、交互次数、一次回复解决率。
  • 新增指标：AI guardrail pass rate、approve / reject rate、not automated reason、route accuracy、response latency。
  • A2A 指标：agent task count、claim latency、artifact returned rate、ownership transfer、reply.delivered success rate。
  • 下一步指标：客户情绪检测、negative feedback、reopen、自动化覆盖率、agent timeout / escalation 和抽查通过率。
SLA及时发现超时风险，而不是事后复盘。
Pass衡量 guardrail 放行率和被拒绝原因。
Route跟踪 billing automation、billing review 与 technical handoff。
A2A跟踪 AgentRelay claim、artifact、delivery 和 timeout。
Sentiment客户情绪异常时及时报警。
07 · Roadmap

三阶段推进：先完成可控通信和行为规范，再接真实证据工具，最后扩大自主调查。

Phase 1 不是终点，而是后续自动化的安全地基。AgentRelay communication foundation 已完成，但没有真实 replay、dashboard、guardrail 和 domain-agent 权限审计，就不进入扩大切流。

批注：演示时这么说

“我希望领导关注的不是今天自动化比例有多高，而是我们有没有一条安全扩大自动化的路径：Phase 1 控制行为，Phase 2 接真实证据工具，Phase 3 才做 governed autonomous investigation。”

批注：准备建议

这里要主动声明边界：AgentRelay communication foundation 已完成，但 SupportPortal 的真实 domain-agent 调查还在 Phase 2。不要在汇报里把它说成已经全自动解决 support case。

Phase 1

自主检测 + 行为规范 + A2A foundation

Zendesk 转发、routing、assignment、guardrail reject / approve、dashboard 指标、真实 case replay，以及 AgentRelay agent-to-agent communication foundation。

Phase 2

辅助调查 + 人 approve

接入 Billing / Log / R&D / Data Agent 和真实 evidence tools；AI 先调查并生成 draft，人做 approve、revise 或 override。

Phase 3

自主调查 + governed Agent-to-Agent

在权限、成本、审计和 guardrail 达标后扩大自主调查，让人转向例外处理、最终责任和质量抽查。

Closing

Phase 1 要证明的不是 AI 会说话，而是 support 系统可以实时检查质量、解释决策、控制风险，并通过 AgentRelay 把跨 Agent 协作变成可审计、可回退的自动化地基。

批注：演示时这么说

“我下一步需要的不是一次性替换 Zendesk，而是批准继续做 Phase 1 小流量验证：真实 case replay、dashboard 指标、billing POC 和 AgentRelay 接入 domain agent 的权限审计。”

批注：准备建议

结束前准备一个明确 ask：要资源、要试点范围，还是要下一阶段评审时间。3 分钟汇报不能只展示页面，必须落到一个决策请求。
