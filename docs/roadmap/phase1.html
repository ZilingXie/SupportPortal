SupportPortal Phase 1

From Zendesk replacement to an AI-native Support System

SupportPortal Phase 1 is a POC for an AI-native support operating system. It is not just a tool replacement: it connects Zendesk forwarding, routing, assignment, AI guardrail, final approval, dashboard, case replay, and AgentRelay communication foundation into one controllable workflow. The Phase 1 goal is to prove that we can reduce reply risk and improve investigation quality without changing the customer entry point or customer experience.

03 · AgentRelay task network

Why AgentRelay matters: private agents collaborate through tasks, not loose chat.

This section answers four questions: why AgentRelay is needed, why not pure A2A protocol, why agents need to communicate, and how an R&D Agent solves questions that the Support Agent cannot solve alone.

Why AgentRelay is neededAgents are not loosely chatting with each other. They exchange tasks, artifacts, and done criteria.
Why not pure A2A protocolMany agents, especially personal agents, have no public IP. The relay handles connection, delivery, audit, and fallback.
Why agents communicateThe Support Agent should not guess. It can hand unresolved questions to R&D / Data / Log Agents for evidence.
How R&D Agent helpsIt reads case context, logs, and repo clues, forms a hypothesis, and returns an evidence artifact, limitation, and next action.
A2A communication path

How agents communicate

  1. 1Support Agent creates a task with request, done criteria, and requester thread.
  2. 2AgentRelay relays the task and records state plus permission boundaries.
  3. 3The target agent claims the task instead of starting a scattered side conversation.
  4. 4The target agent submits an artifact with evidence, limitations, and recommended next action.
  5. 5reply.delivered returns to the original thread, and the requester-side owner decides whether to close.
R&D Agent investigation loop

How the R&D Agent investigates

  1. 1Receives the support question, environment, reproduction context, and known constraints.
  2. 2Reads case context, logs, repo clues, or known knowledge to form a hypothesis.
  3. 3Produces an evidence artifact with basis, verifiable proof, missing data, and risk boundary.
  4. 4Returns the next action: continue investigation, request more info, escalate, or form a customer-safe conclusion.
R&D Agent example

Example: Support asks whether a screen sharing interruption was intentional or abnormal.

This is the kind of support question that should not be answered by guessing. The R&D Agent checks event evidence and returns a clear conclusion, proof trail, and customer-safe boundary.

Question

Question: Please check channel 42175037575290 (streamer 652NyjgkrD07HOf_KVjkhw); the screen sharing session was interrupted at timestamp 01:28:44:649. Could you determine whether this was caused by the user calling the unpublish API or if it was an abnormal disconnection?

R&D Agent

Investigation complete (390.3s)

Conclusion: This was an intentional unpublish call initiated by the user/application, not an abnormal interruption.

Key evidence:

  • Channel: 42175037575290, CallId: 6a3b3201a3fff75800885094.
  • Broadcaster: 652NyjgkrD07HOf_KVjkhw, uid: 8933524, SID: C4E3D88760726EEEC8668FDE2B825157.
  • Screen sharing track: track-scr-v-754e053e.
  • 2026-06-24 01:28:44.686 UTC: Argus recorded Client.unpublish with success=1; errorCode and errorMsg were empty.
  • Between 01:28:47.348 and 01:28:47.350 UTC, the same track underwent LocalVideoTrack.stop, unpipe, and close operations, all with success=1.
  • No webSocketQuit, WebQuit, uquit, ICE disconnection, or connection loss occurred around this time; the broadcaster's actual Client.leave happened later, at 01:31:24 UTC.

Therefore, the disconnection of screen sharing around 01:28:44.649 was caused by the application calling Client.unpublish(["track-scr-v-754e053e"]) and subsequently closing the local screen track.

04 · Role shift

AI is not replacing support engineers; it is productizing daily manager quality checks.

The customer-facing experience stays unchanged. Engineers are freed from repetitive process work. AI agents handle real-time checks, assisted investigation, and cross-system collaboration.

Before

  • Managers could only sample replies, not check every technical detail, boundary, and SLA risk.
  • Customer dissatisfaction was usually discovered after complaints, too late for sentiment or handoff risk.
  • Engineers repeatedly copied context into external AI tools, making the process hard to audit or reuse.

After

  • Every reply goes through AI guardrail before it can reach the customer.
  • Every customer message can be checked for sentiment and SLA risk before escalation becomes visible.
  • Support Agent can use AgentRelay to coordinate Billing, Log, R&D, and Data Agents, while humans and guardrails control customer-visible output.
05 · Showcase

Showcase: how AI Guardrail rejects an incomplete reply.

This case shows the core quality value of Phase 1. The system is not merely making language more polite; it blocks replies that lack conclusion, proof, next step, and customer-safe boundary before customers see them.

Bad case: traditional support quality failure

A fast but ungrounded answer can turn a technical issue into an angry customer.

This is the traditional support pain point: how do we ensure reply quality, and how do we monitor it before the customer sees the damage?

Guardrail changes the control point

Instead of finding bad replies after review, Phase 1 checks quality before a customer-visible reply is approved.

Traditional support can measure response time, but quality problems often surface only after the customer reacts. The guardrail demo below shows the same failure mode stopped earlier: missing proof, missing next step, and unsafe root-cause claims are rejected before send.

06 · Dashboard

Management metrics must move from the SLA era to the AI guardrail era.

Traditional metrics still matter, but Phase 1 also tracks whether AI is actually reducing risk, improving quality, and explaining why some cases should not be automated yet.

  • Traditional metrics: first response time, second response time, and SLA.
  • Core new metrics: AI guardrail pass rate, agent interaction count, and first-contact resolution.
  • Quality explanation metrics: guardrail reject reason, not automated reason, and route accuracy.
  • Future extension metrics: agent claim latency, artifact returned rate, reply.delivered success rate, sentiment alerts, and reopen.

07 · Roadmap

Three stages: controlled behavior first, real evidence tools second, autonomous investigation last.

Phase 1 is not the endpoint. It is the safety foundation for later automation. AgentRelay communication foundation is ready, while real SupportPortal domain-agent investigation remains a Phase 2 integration.

Phase 1

Self-check + behavior policy + A2A foundation

Zendesk forwarding, routing, assignment, guardrail reject / approve, dashboard metrics, real case replay, and AgentRelay agent-to-agent communication foundation.

Phase 2

Assisted investigation + human approval

Connect Billing / Log / R&D / Data Agents and real evidence tools. AI investigates and drafts first; humans approve, revise, or override.

Phase 3

Autonomous investigation + governed Agent-to-Agent

After permission, cost, audit, and guardrail gates are met, expand autonomous investigation and move humans toward exception handling, final accountability, and quality sampling.

Closing

Closing: what Phase 1 must prove

Phase 1 is not proving that AI can talk. It must prove that the support system can check quality in real time, explain decisions, control risk, and use AgentRelay to turn cross-agent collaboration into an auditable and reversible automation foundation.

If Phase 1 works, support is not merely moving away from Zendesk. It is moving from an SLA-driven manual process toward AI-native quality management, evidence collaboration, and controlled automation.
