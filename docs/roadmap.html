SupportPortal Roadmap

整体落地优化计划

  • 项目定位：建设基于 agent 的工单系统，不把 AI 包装成完全替代真人的 support engineer。
  • 当前阶段：Billing、Routing、Assignment、Multi-Agent、RAG/KG 都以可审计试运行为优先级。
  • Phase 1/2/3 门禁：先做工单系统雏形，再扩大 AI 主动处理，最后进入 agent-to-agent 高自动化。
  • 近期 POC：验证 billing route、邮件回执、engineer reply 通过/拒绝、dashboard 指标和真实 case 模拟。
总计划追踪

Phase 1/2/3 阶段门禁

用三段门禁追踪落地：工单雏形先稳定，AI 主动处理再扩量，agent-to-agent 放到长期。

进行中

Phase 1：效率提升 + 工单系统雏形

  • Zendesk 转发到内部系统，保留现有客户前端和渐进 AB test 出口。
  • billing 自动化 POC 先跑 invoice、account fraud / deactivate 等确定性 case。
  • AI guardrail 检查真人回复的 conclusion、proof、next step，并支持通过/拒绝。
  • Dashboard 展示 SLA、通过率、case 状态和人工审核结果。
  • 准备 1% 小流量切流前的真实 case 回放和幂等验证。
下一阶段

Phase 2：AI 主动处理 + 人 approve

  • AI 先调查、生成 AI draft，人做 approve / revise / override。
  • 客户可见回复必须经过敏感信息 guardrail，内部证据不直接外泄。
  • 逐步扩大 billing 之外的可自动化类型，质量低于门禁时回退人工。
  • 小流量切流后统计覆盖率、误判率、Not automated 原因和客户反馈。
  • 用质量指标决定哪些 case 可以从人工审核降级为抽查。
长期方向

Phase 3：agent-to-agent + 高自动化

  • Support agent 接入研发 agent、数据 agent、日志 agent 或专用 skill。
  • 探索 hub / forum / A2A 协议，解决 agent 之间没有固定 endpoint 的协作问题。
  • 限制 retry、并发和 token 预算，避免 T1 无限追问造成成本失控。
  • 企业级合规审计先行：权限、历史记录、敏感信息、source of truth 都要可证明。
  • 当 AI 能稳定解决大多数 case 后，人转向例外处理、最终责任和质量抽查。

    Engineer AI Agent 架构

    这张 Mermaid 图固定当前讨论后的 multi-agent 生命周期：client escalation 先被总结成可审计 packet，再进入 AI 调查循环，最后由工程师和 guardrail 共同完成客户回复。

    Summary → Plan → Execute → Review → Guardrail

    Summary/Plan/Execute/Review 第一版已接入 escalation runtime，revise 会携带 engineer feedback、上一轮 evidence 和 review problem statement 回到 Plan Agent；mem0 和 skill list 未完成时 Plan Agent 使用 deterministic fallback。

    flowchart TD
  C["Client AI handle 不了客户问题"] --> E["Escalate to Engineer"]
  E --> S["Summary Agent: 整理上下文、线索、缺失信息和 redaction boundary"]
  S --> T["Create Engineer Ticket with summary packet"]
  T --> P["Plan Agent: summary packet + mem0 + skill list / fallback"]
  P --> X["Execute Agent: 调度 allowlisted subagents"]
  X --> G["Evidence packet + task results"]
  G --> R["Review Agent: 判断下一步"]
  R -->|ready_for_engineer| F["告诉工程师发现"]
  R -->|replan_required, max 2 retries| P
  R -->|unable_to_resolve| U["告诉工程师目前信息无法回答或解决"]
  F --> H["Engineer 操作"]
  U --> H
  H -->|revise| P
  H -->|approve| Q["Guardrail: 生成或校验 customer-facing reply"]
  Q --> A["Engineer final approve"]
  A --> Y["回复客户"]
  Y --> Z["关闭 Engineer 工单"]
  Z --> M["写 audit event + Case Memory candidate"]

    Review Agent 的三种决策是 ready_for_engineer、replan_required、unable_to_resolve；关闭工单后只写 Case Memory candidate，不自动晋升 active memory。

    主线进度

    每条主线都按“目前已经能证明什么”和“下一步还要交付什么”拆开，避免把计划文档、原型和可上线能力混在一起。

    没有匹配的主线或任务。

    Routing 优化计划

    承接 Routing rules lane 已识别但未落地的能力升级，按高/中/低优先级排列；每条都对应 backend/services/support_router.py 的具体改造点。

    高优先级

    安全与可观测先行

    直接影响 billing automation 边界与产线路由的可调诊性；不落地这两条，后续阈值调整与灰度扩面都缺乏反馈信号。

    1. routing-deterministic-policy-gate

      Deterministic billing 决策也走 minimal policy gate：refund / dispute / legal / compensation 关键词 sniff 命中即降级到 billing_review，避免白名单吞掉风险信号（例如「Account suspended, please refund」当前会被 account_suspension 白名单命中，refund 信号被丢失）。

      Safety _heuristic_route_decision

    2. routing-decision-observability

      在 decide_support_route 出口加 structured log + metrics（route / scope_label / router_source / fallback_reason / model_confidence），并基于已有 support_billing_tickets 字段在 admin 页跑 daily 聚合，让 fallback rate、误判率、置信度分布有可视化看板。当前 schema 字段齐全，但缺监控管道，没法量化路由质量。

      Observability decide_support_route
    中优先级

    架构与正确性升级

    提升路由判别的颗粒度与一致性；为 phase 2/3 automation 灰度扩面铺路。

    1. routing-per-scope-threshold

      per-scope confidence threshold：billing automation ≥0.85、refuse / web_search 可放宽到 0.6，由 env 覆盖。当前单一 INTENT_ROUTER_CONFIDENCE_THRESHOLD=0.7 对所有 scope 一视同仁，未反映 automation 与 refuse 的风险代价差异。

      Architecture decide_support_route

    2. routing-risk-flag-taxonomy

      把 LLM 输出的 risk_flags 归一化到固定枚举，policy gate 统一改 exact set match，移除 substring 判断。当前 _apply_policy_gate 同时用 set membership 和「"legal" in flag」substring，规则不一致、容易误中或漏中边界 case。

      Safety _apply_policy_gate

    3. routing-semantic-first-layered

      semantic-first 模式（/account）下强信号 deterministic（billing 白名单等）优先于 LLM；只把弱信号 deterministic（gratitude / 短 troubleshooting）放到 LLM 之后。当前 TK-ACC-C31612 修复后所有 deterministic 都被让到 LLM 之后，等于让中等置信 LLM 误判覆盖了高精度白名单。

      Architecture decide_support_route(semantic_first)

    4. routing-conversation-aware-heuristic

      _heuristic_route_decision 引入 latest_assistant_message.source 与历史，在长会话延续场景（如「thanks, but it still happens」）避免短消息独立判断；当存在 engineer_guidance 历史时优先 ticket_resolution 检测，避免误进短 troubleshooting fast path。

      Accuracy _heuristic_route_decision

    5. routing-pipeline-refactor

      抽 RouteRequest dataclass + 单一 _route_pipeline(request, llm_first) 主循环，消除 semantic-first 与默认分支的复制实现。当前两条路径共享 LLM 调用、threshold 读取、heuristic fallback、conservative fallback 的所有逻辑，但用复制实现，后续加字段时必须改两处，容易漏。

      Refactor support_router.py
    低优先级

    结构清理与韧性补强

    本身不阻塞 phase 2/3，但在加新 fast path 与 prompt 迭代频率上升时积累价值。

    1. routing-heuristic-split

      拆 _heuristic_route_decision 为 ordered chain of sub-matchers（_match_billing_whitelist / _match_resolution / _match_gratitude / _match_short_troubleshooting / _match_api_mismatch / _match_join_channel / _match_product_portfolio）。当新增 fast path 频率上升时（plan_change / pricing_inquiry 等），让分支顺序约束显式化，避免 reviewer 必须重读 ~150 行才能确认插入位置。

      Refactor _heuristic_route_decision

    2. routing-automation-candidate-cleanup

      删除 _llm_route_decision 的 billing action set 里 dead value automation_candidate（未在 policy gate 任何分支处理，最终默认落到 human_review_required），或给它明确语义。

      Cleanup _llm_route_decision

    3. routing-threshold-env-cache

      INTENT_ROUTER_CONFIDENCE_THRESHOLD 改 module 级 lru_cache + 测试 reset 钩子，避免热路径每请求 parse env；与 per-scope threshold 落地时一并实现。

      Perf _safe_float_env

    4. routing-llm-transient-retry

      _llm_route_decision 对网络/超时类异常加 1 次指数退避重试（200ms），不重试 invalid_json / invalid_payload。避免瞬态网络抖动让 billing 工单错误进入 conservative_agora_technical_fallback。

      Reliability _llm_route_decision
