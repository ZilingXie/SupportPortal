SupportPortal Roadmap

整体落地优化计划

  • 项目定位：建设基于 agent 的工单系统，不把 AI 包装成完全替代真人的 support engineer。
  • 当前阶段：Phase 1 已完成，Phase 2 进入 9/1 Controlled Launch 实施与验证；正式入口是 /workspace 与 /workspace/admin。
  • 9/1 主链路：Billing automation、Not automated Engineer Case 切量、邮件邀请与 weekly schedule 约束的系统派单、3 小时 SLA、guardrail approve/final approve、Outlook reply 和 Admin 管理闭环。
  • 边界：Engineer multi-agent 与 AgentRelay 真实 case 集成不进入 9/1 交付主链路；旧 /engineer UI 是 legacy，但 /api/engineer/* 仍是 active backend contract。
总计划追踪

Phase 1 完成，Phase 2 进入 9/1 Controlled Launch

Phase 2 的 P0、P1、P2 都属于 9/1 交付范围；优先级只决定实施顺序，不代表低优先级项目可以延期到 9/1 之后。

  • AgentRelay communication foundation 已完成：A2A-shaped task relay、MCP tools、token auth、thread reuse、completion ownership 和 audit events。

Phase 2：Billing automation + Engineer Case 生产闭环

  • P0：生产账号与 RBAC、Admin 创建账号、available/unavailable 管理及完整操作审计。

  • P2：完成 Admin metrics、action-specific 内部邮箱配置和真实 case 全量流转接入。
  • Billing 内部处理统一通过 Outlook reply；所有客户回复必须经过 guardrail 与 engineer final approve。

Phase 3：Engineer multi-agent + governed agent-to-agent

  • Engineer multi-agent 默认关闭，不影响 9/1 Workspace、派单、Billing 与 guardrail 主链路。
  • 后续再在 AgentRelay foundation 上扩大 Support agent 与研发、数据、日志 agent 的协作范围。
  • 重点从“能通信”转向“能自主调查”：权限、证据质量、成本、endpoint/forum/hub 协作和审计协议必须达标。
  • 限制 retry、并发和 token 预算，避免 T1 无限追问造成成本失控。
  • 企业级合规审计先行：权限、历史记录、敏感信息、source of truth 都要可证明。
  • 当 AI 能稳定解决大多数 case 后，人转向例外处理、最终责任和质量抽查。

    Engineer AI Agent 架构

    这张 Mermaid 图固定当前讨论后的 multi-agent 生命周期：client escalation 先被总结成可审计 packet，再进入 AI 调查循环，最后由工程师和 guardrail 共同完成客户回复。

    Summary → Plan → Execute → Review → Guardrail

    Summary/Plan/Execute/Review 第一版已接入 escalation runtime：Engineer 工单默认只走 summary packet 与 guardrail-only 工作流，工程师点击 investigating 后才运行并打开 multi-agent workspace；workspace 打开后工程师消息携带 multi_agent_enabled=true 触发一轮 Plan/Execute/Review 刷新；revise replan 循环与 max 2 retries 当前已暂停（只保留可编辑/重新走 guardrail）；mem0 和 skill list 未完成时 Plan Agent 使用 deterministic fallback。

    flowchart TD
  C["Client AI handle 不了客户问题"] --> E["Escalate to Engineer"]
  E --> S["Summary Agent: 整理上下文、线索、缺失信息和 redaction boundary"]
  S --> T["Create Engineer Ticket with summary packet"]
  T --> P["Plan Agent: summary packet + mem0 + skill list / fallback"]
  P --> X["Execute Agent: 调度 allowlisted subagents"]
  X --> G["Evidence packet + task results"]
  G --> R["Review Agent: 判断下一步"]
  R -->|ready_for_engineer| F["告诉工程师发现"]
  R -->|replan_required 当前暂停自动回路| F
  R -->|unable_to_resolve| U["告诉工程师目前信息无法回答或解决"]
  F --> H["Engineer 操作"]
  U --> H
  H -->|revise| V["编辑备注 + 重新走 guardrail；不自动 replan"]
  V --> H
  H -->|approve| Q["Guardrail: 生成或校验 customer-facing reply"]
  Q --> A["Engineer final approve"]
  A --> Y["回复客户"]
  Y --> Z["关闭 Engineer 工单"]
  Z --> M["写 audit event + Case Memory candidate"]

    Review Agent 的三种决策是 ready_for_engineer、replan_required、unable_to_resolve；关闭工单后只写 Case Memory candidate，不自动晋升 active memory。

    Routing 优化计划

    承接 Routing rules lane 最新审阅结论，按 P0 安全边界、P1 可观测与灰度门禁、P2 架构清理排列；覆盖 router、billing review 体验、replay set 与 dashboard 指标。

    高优先级

    P0：安全边界先补

    先封住会触发错误 automation 或把 billing 风险错送 RAG 的入口；这些问题不依赖大重构，应该在继续扩 automation 前完成。

    1. routing-deterministic-policy-gate

      已完成：Deterministic billing 白名单已接入 minimal risk gate；refund / dispute / legal / compensation / overcharge 关键词 sniff 命中即降级到 billing_review，避免「Account suspended, please refund」被 account_suspension 白名单直接送进 billing_automation。

      Safety _heuristic_route_decision Done

    2. routing-fallback-billing-risk-sniff

      conservative_agora_technical_fallback 前增加 billing-risk sniff：当 LLM missing_credentials / timeout / low confidence 时，如果最新消息含 invoice wrong、refund、dispute、legal、restore access 等风险信号，进入 billing_review，而不是默认 agora_technical / rag。

      Safety decide_support_route conservative_fallback

    3. routing-billing-review-customer-experience

      billing_review 的客户可见回复改成「已收到，将由 billing/support team 人工审核」并创建内部待办/queue；不要继续复用 non_agora refusal copy，避免客户看到「不在支持范围内」这类错误语义。

      Customer Experience resolve_support_message billing_review
    中优先级

    P1：可观测与灰度门禁

    P0 安全洞补齐后，先把 route 质量量化，再调阈值或扩大 automation；没有指标就不扩大 Controlled Launch 流量。

    1. routing-decision-observability

      在 decide_support_route 出口加 structured log + metrics（route / scope_label / router_source / fallback_reason / model_confidence），并基于已有 support_billing_tickets 字段在 admin 页跑 daily 聚合，让 fallback rate、纠正率、置信度分布和 not_automated_reason 有可视化看板。

      Observability decide_support_route dashboard

    2. routing-real-zendesk-replay

      扩展真实 Zendesk replay set：invoice request、account suspension、company verification、technical handoff、非 billing、mixed-risk billing negative set 都要可离线重放，用 replay 指标决定是否继续扩大 automation。

      Evaluation Replay Golden Set

    3. routing-per-scope-threshold

      per-scope confidence threshold：billing automation ≥0.85、refuse / web_search 可放宽到 0.6，由 env 覆盖。当前单一 INTENT_ROUTER_CONFIDENCE_THRESHOLD=0.7 对所有 scope 一视同仁，未反映 automation 与 refuse 的风险代价差异。

      Architecture decide_support_route

    4. routing-risk-flag-taxonomy

      把 LLM 输出的 risk_flags 归一化到固定枚举，policy gate 统一改 exact set match，移除 substring 判断。当前 _apply_policy_gate 同时用 set membership 和「"legal" in flag」substring，规则不一致、容易误中或漏中边界 case。

      Safety _apply_policy_gate

    5. routing-semantic-first-layered

      semantic-first 模式（/account）下强信号 deterministic（billing 白名单等）优先于 LLM；只把弱信号 deterministic（gratitude / 短 troubleshooting）放到 LLM 之后。当前 TK-ACC-C31612 修复后所有 deterministic 都被让到 LLM 之后，等于让中等置信 LLM 误判覆盖了高精度白名单。

      Architecture decide_support_route(semantic_first)

    6. routing-conversation-aware-heuristic

      _heuristic_route_decision 引入 latest_assistant_message.source 与历史，在长会话延续场景（如「thanks, but it still happens」）避免短消息独立判断；当存在 engineer_guidance 历史时优先 ticket_resolution 检测，避免误进短 troubleshooting fast path。

      Accuracy _heuristic_route_decision
    低优先级

    P2：结构清理与韧性补强

    不阻塞安全收口和灰度判断，但能降低后续新增 intent、prompt 和 fast path 的维护成本。

    1. routing-pipeline-refactor

      抽 RouteRequest dataclass + 单一 _route_pipeline(request, llm_first) 主循环，消除 semantic-first 与默认分支的复制实现。当前两条路径共享 LLM 调用、threshold 读取、heuristic fallback、conservative fallback 的所有逻辑，但用复制实现，后续加字段时必须改两处，容易漏。

      Refactor support_router.py

    2. routing-heuristic-split

      拆 _heuristic_route_decision 为 ordered chain of sub-matchers（_match_billing_whitelist / _match_resolution / _match_gratitude / _match_short_troubleshooting / _match_api_mismatch / _match_join_channel / _match_product_portfolio）。当新增 fast path 频率上升时（plan_change / pricing_inquiry 等），让分支顺序约束显式化，避免 reviewer 必须重读 ~150 行才能确认插入位置。

      Refactor _heuristic_route_decision

    3. routing-automation-candidate-cleanup

      删除 _llm_route_decision 的 billing action set 里 dead value automation_candidate（未在 policy gate 任何分支处理，最终默认落到 human_review_required），或给它明确语义。

      Cleanup _llm_route_decision

    4. routing-threshold-env-cache

      INTENT_ROUTER_CONFIDENCE_THRESHOLD 改 module 级 lru_cache + 测试 reset 钩子，避免热路径每请求 parse env；与 per-scope threshold 落地时一并实现。

      Perf _safe_float_env

    5. routing-llm-transient-retry

      _llm_route_decision 对网络/超时类异常加 1 次指数退避重试（200ms），不重试 invalid_json / invalid_payload。避免瞬态网络抖动让 billing 工单错误进入 conservative_agora_technical_fallback。

      Reliability _llm_route_decision
