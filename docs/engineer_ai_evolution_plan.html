SupportPortal Engineer AI 多 Agent 演进计划

本计划暂停 EvoAgentX 计划，把线上工程师端主链路调整为受控 Engineer Multi-Agent 调查流程；现有 Engineer AI guardrail 功能继续保留，作为工程师批准后的客户安全校验。

状态：线上 multi-agent 主链路规划 范围：Engineer AI only 日期：2026-06-11 语言：中文

一、核心结论

推荐方向：EvoAgentX 计划暂停；线上 Engineer AI 从 guardrail-only 升级为 Engineer Multi-Agent 主链路。新流程是 engineer 端工单创建后触发多 agent 调查，Conclude Agent 给出结论，工程师批准或 revise；批准后必须经过现有 Engineer Guardrail，revise 后重新进入 Plan Agent 流程。

二、架构边界

Client AI

继续使用现有 RAG official_only 主链路。客户侧回答只基于官方知识，不纳入 EvoAgentX 自进化范围。

Engineer AI Runtime

线上主链路升级为 Engineer Multi-Agent Investigation；继续使用 engineer_case、engineer_agent_state、handoff_packet、evidence_tools 作为生产执行和审计 source of truth。

EvoAgentX 计划暂停

当前不引入 EvoAgentX 作为优化实验室，也不让外部 optimizer 产生线上候选拓扑；先把多 agent 调查闭环做成可审计、可批准、可 revise 的生产主链路。

Case Memory Layer

保存工程师确认后的案例摘要，用于相似案例检索和上下文增强。Mem0、agentmemory、Postgres + pgvector 都是候选 provider；Postgres 仍保存权威工单、反馈、评估和版本记录。

治理原则

Plan、Review、Implement、Conclude 只能服务工程师调查；客户回复仍必须经工程师批准和 Engineer Guardrail，任何 agent 都不能绕过审批、权限和审计日志。

三、目标与非目标

类别 内容 说明
目标 降低工程师纠正率 通过 Plan Agent、Memory Review Agent、Implement Agent 和 Conclude Agent 的受控协作，让 engineer AI 更快给出可审查结论。
目标 提升相似案例复用 Case Memory Layer 只保存已确认案例，诊断时检索相似症状、根因、证据和解决方案。
目标 上线可 revise 的多 agent 调查闭环 工程师可以批准 conclusion，也可以指出 agent 做错了什么或下一步该做什么；revise 后重新走 Plan Agent 流程。
非目标 替换 client AI RAG client AI 继续 official_only RAG，不引入 Case Memory Layer 案例记忆作为客户直接回答依据。
非目标 自动跳过工程师审批 工程师审批和客户安全校验是硬边界，不允许任何 agent 改写或绕过。
非目标 继续推进 EvoAgentX EvoAgentX 计划暂停；当前阶段不做离线 optimizer、shadow optimizer 或自动候选版本生成。
非目标 让记忆层成为事实源 Case Memory Layer 是检索增强层；权威记录、审计和版本仍在 SupportPortal 数据库。

四、数据流

1. 工单创建

engineer 端工单创建后，系统基于 client ticket、handoff packet 和历史 investigation state 启动线上 Engineer Multi-Agent 主链路。

2. 多 Agent 调查

Plan Agent 创建调查计划，Memory Review Agent 结合 Active Retrieval Memory 优化计划并标记顺序或并行，Implement Agent 执行证据任务。

3. Conclude

Conclude Agent 汇总 evidence packet，给出 conclusion、置信度、风险、缺失信息和建议客户草稿。

4. 工程师审查

工程师可以 approve，也可以 revise：告诉 agent 下一步该做什么，或指出哪里做错。工程师 revise 后重新进入 Plan Agent。

5. Guardrail

工程师批准后必须再走现有 guardrail，校验客户安全、内部信息泄露和 root cause 夸大风险，只有通过后才进入客户回复流程。

四 A、线上 Engineer Multi-Agent 主链路

主链路定位：现在线上 engineer AI 的 guardrail 功能保留，但不再让它承担完整调查职责。新增 multi-agent 调查链路负责计划、记忆审查、证据执行和总结；guardrail 只在工程师批准后做最终安全校验。

Agent / 模块 职责 输入 输出 边界
Plan Agent 根据上下文、可用 skill/tool 列表和 engineer revise 指令创建调查计划。 client ticket、handoff_packet、engineer_agent_state、历史 investigation messages、revise note。 结构化 plan：目标、假设、任务、所需证据、风险、每步依赖。 不直接调用工具，不生成客户最终回复。
Memory Review Agent 检索 Active Retrieval Memory 和相关历史经验，优化计划，并判断执行顺序与是否可并行。 Plan Agent 输出、Active Retrieval Memory、Case Memory Layer 检索结果。 reviewed_plan、dependency graph、parallel groups、blocked reasons、历史不要做的事。 不能读取 inactive ledger；不能把未确认记忆当事实。
Implement Agent 按 reviewed_plan 顺序或并行执行调查任务，调用允许的 evidence tools、internal RAG、official RAG fallback 和只读上下文摘要。 dependency graph、tool allowlist、证据任务参数。 task results、evidence_refs、失败原因、仍缺信息。 只做调查和证据收集，不审批、不发送客户回复、不写长期记忆。
Conclude Agent 整合所有任务结果，生成给工程师看的 conclusion。 reviewed_plan、task results、evidence packet、guardrail policy。 conclusion、confidence、root cause status、customer-safe draft、risk flags、next action。 conclusion 只给 engineer 审查；客户草稿必须等待工程师 approve 和 Engineer Guardrail。
Engineer Guardrail 保留现有线上 guardrail 功能，在工程师批准后执行最终安全校验。 工程师批准的 conclusion / customer draft、evidence packet、customer-safe policy。 pass / fail、失败原因、安全改写建议或请求重新 revise。 guardrail 不做完整调查；只负责批准后的安全边界。
Approve 路径

Conclude Agent 输出 conclusion 后，工程师点击 approve；工程师批准后必须再走现有 guardrail，通过后才允许客户回复进入发送或沟通流程。

Revise 路径

工程师 revise 时必须保存 revise note，说明 agent 做错了什么或下一步该做什么；工程师 revise 后重新进入 Plan Agent，并把上一轮 plan、evidence 和错误反馈纳入上下文。

后续学习 Agent：不放入第一版线上闭环。等 ticket 关闭且结论被确认后，再由独立 learning agent 总结整个流程，提炼最佳实践和不该做的事，经过脱敏、安全标签和人工或规则晋升后，才进入 Mem0 / Case Memory Layer 候选。

五、RAG 与 Case Memory Layer 知识边界

不要按 official / non-official 粗暴切分。更稳的规则是：RAG 放可引用、可追溯、文档型知识；Case Memory Layer 放已确认案例、经验、偏好和调查记忆。Mem0 和 agentmemory 都只是候选 provider。

知识类型 推荐归属 使用方 原因
官方文档 RAG official_only Client AI；Engineer AI fallback 需要稳定引用、版本追踪、citation 和客户安全边界。
内部技术文档 / runbook / troubleshooting docs RAG non_official_only Engineer AI 仍属于文档型知识，需要 chunk、BM25/FTS/vector、source path、访问控制和可追溯证据。
工程师确认案例 Postgres + Case Memory Layer 摘要 Engineer Multi-Agent；replay eval 适合语义召回相似症状、根因、证据和解决方案，但权威记录仍在 Postgres。
工程师纠正 / 复盘 Postgres + Case Memory Layer selected memory Engineer Multi-Agent；revise loop；后续学习 agent 结构化反馈用于评估和优化；只有确认后、脱敏后的摘要才进入长期记忆。
客户偏好 / 历史处理习惯 Case Memory Layer Engineer AI 偏好和历史上下文更像记忆，不适合混进文档检索索引。
未确认 AI 草稿 / 猜测 不进入长期记忆 仅短期上下文 避免自进化污染记忆；未验证 root cause 不能被长期召回。
错误切分

official doc 进 RAG；其他所有知识进某个记忆 provider。这个做法会让内部 runbook 和技术文档失去 citation、版本、检索策略和访问控制。

推荐切分

official/internal 文档都进 RAG，但用 access mode 隔离；confirmed cases、纠正经验和客户偏好进入 Case Memory Layer。

Engineer Evidence 推荐顺序

1. Case Memory

查相似 confirmed cases，获得历史症状、根因、证据和解决方案。

2. Internal RAG

用 non_official_only 查内部技术文档、runbook 和排障资料。

3. Official RAG

需要 API 语义、客户安全引用或官方依据时 fallback official_only。

4. Evidence Packet

合并案例记忆、内部文档证据和官方引用，标记 internal/customer-safe 边界。

5. Draft / Ask

证据足够则生成客户草稿待审批；不足则向工程师请求下一项证据。

六、RAG 技术文档去重治理

重复或相似技术文档不应直接迁入 Case Memory Layer。这类问题应该在 RAG ingestion 和 retrieval 层治理：RAG 负责 exact dedupe、near-duplicate clustering、canonical document selection、metadata alias 和 citation；Case Memory Layer 只保存从已确认案例中提炼出的经验记忆。

场景 推荐处理 归属
完全重复文档 用 source_id、source_url、content_hash 或 normalized_content_hash 做 skip/upsert，避免重复 chunk 进入主索引。 RAG ingestion
同一文档不同版本 最新或正式版本标为 primary；旧版本标记 archived/shadow，并保留 version、superseded_by、effective_at metadata。 RAG ingestion + metadata
多篇技术文章讲同一问题 聚成 canonical topic，选权威、最新、最完整的一篇或一组 chunk 作为 primary；其他文档作为 alias/source support。 RAG canonicalization
内容相似但结论冲突 不要自动合并。标记 conflict，进入人工 review 或规则判定，避免错误覆盖有效证据。 RAG governance
多个工程师案例指向同一根因 合并或更新 case memory，保留 related_ticket_ids、related_canonical_doc_ids 和 confidence。 Case Memory Layer + Postgres
历史处理偏好、常见坑、复盘经验 沉淀为 selected memory，服务 engineer AI 的经验召回，不作为文档 citation。 Case Memory Layer

推荐治理流水线

1. Normalize

统一格式、标题、URL、空白、代码块和 boilerplate，生成稳定 hash。

2. Exact Dedupe

通过 content hash 和 source identity 跳过或更新完全重复文档。

3. Near Duplicate

用 embedding、simhash 或 minhash 聚类相似文档，形成候选 canonical group。

4. Canonical Select

按权威性、新鲜度、完整度和产品匹配选择 primary 文档或 primary chunk。

5. Index + Alias

primary 进入 RAG 主索引；重复文档保留 alias、archived、related_source metadata。

RAG 的职责

保证文档证据可引用、可追溯、可版本治理。重复文档治理要影响 chunk、rank、citation 和 source metadata。

Case Memory Layer 的职责

把多个确认案例沉淀成更紧凑的经验记忆，例如 symptom、confirmed root cause、evidence pattern、resolution 和 related ids。具体 provider 通过 POC 决定。

Case Memory Ledger 与 Active Retrieval Memory

阶段 2A 原则：所有 feedback 都进入 Case Memory Ledger；Engineer AI 只自动检索 Active Retrieval Memory。Ledger 是完整审计账本，Active Retrieval Memory 是经过人工或规则晋升后的可召回知识子集。

层级 写入范围 默认状态 用途
Case Memory Ledger approve、revise、reject、resolve、reopen 等所有结构化 HITL feedback。 support_case_memory_ledger；retrieval_enabled=false；active_memory_status=inactive。 保留学习来源、纠正内容、质量标签、安全标签和版本字段，供审计、复盘、晋升和离线 eval 使用。
Active Retrieval Memory 只包含从 Ledger 中通过安全、质量和确认门禁晋升的记录。 retrieval_enabled=true；active_memory_status=active。 后续阶段作为 Engineer AI 的自动相似案例召回来源；不会直接暴露给 client AI。
Ledger 状态流

ledger_only 表示只保留审计；candidate 表示可进入晋升审查；active 表示已进入主动召回；rejected 或 superseded 表示被否决或被新记录替代。

Phase 2A 不做的事

不接入 Mem0，不让 Engineer AI 自动检索 Ledger，不把 memory_candidate 直接等同于 confirmed case。

    所有 HITL feedback 写入 support_case_memory_ledger；默认关闭 retrieval_enabled，只把通过晋升门禁的记录留给后续 Active Retrieval Memory。

    后端 / 记忆

  • 接入线上 Engineer Multi-Agent 主链路

    在 engineer 端工单创建后启动 multi-agent orchestrator，保留现有 Engineer Guardrail 作为工程师 approve 后的最终安全门禁。

    后端

  • 实现 Plan Agent

    根据 ticket、handoff_packet、skill/tool 列表和 engineer revise note 创建结构化调查计划，输出目标、假设、任务、依赖和风险。

    后端 / Agent

  • 实现 Memory Review Agent 与调度判断

    只检索 Active Retrieval Memory，优化计划，标记 sequential / parallel / blocked，并输出 dependency graph 和历史不要做的事。

    后端 / 记忆

  • 实现 Implement Agent 执行层

    按 reviewed_plan 顺序或并行执行只读 evidence tasks，调用 allowlisted tools、internal RAG、official fallback，并记录 evidence_refs 和失败原因。

    后端 / Agent

  • 实现 Conclude Agent

    汇总 plan、memory review 和 task results，给 engineer 输出 conclusion、confidence、risk flags、缺失信息和 customer-safe draft 候选。

    后端 / Agent

  • 实现工程师 approve / revise 闭环

    approve 后必须进入 Engineer Guardrail；revise 时保存工程师指出的问题或下一步指令，并重新触发 Plan Agent。

    后端 / UI

  • 定义 Case Memory Layer 写入规则

    只写入 confirmed 案例；做摘要、脱敏、internal/customer-safe 字段隔离，并保留 provider 可替换性。

    RAG / 记忆

  • 固化 RAG 与 Case Memory Layer 知识边界

    文档型知识保留在 RAG access modes；经验、案例和偏好进入 Case Memory Layer，避免把所有非官方知识迁入记忆层。

    架构 / RAG

  • 接入相似案例检索

    在 engineer evidence 阶段检索 confirmed cases，并与 internal RAG、official fallback 合并成统一 evidence packet。

    后端

  • 建立 RAG 技术文档去重治理

    在 ingestion/retrieval 层实现 exact dedupe、near-duplicate clustering、canonical selection、alias metadata 和 conflict review。

    RAG

  • 建立离线评估集

    从 feedback、revise notes 和 approved conclusions 生成 multi-agent replay eval，覆盖计划质量、证据充分性、客户安全和 guardrail 拦截。

    评估

  • 暂停 EvoAgentX 优化实验室

    EvoAgentX 计划暂停；当前阶段不搭建 optimizer，不生成自动候选版本，等线上 multi-agent 闭环稳定后再重新评估。

    架构

  • 建立 shadow eval 门禁

    上线前以 shadow / replay 方式评估 multi-agent 主链路，不生成 EvoAgentX 候选版本；安全失败一票否决。

    质量

  • 灰度与回滚

    用 feature flag 控制新版本流量，记录指标，失败时快速回滚到上一稳定版本。

    运维

十一、质量门禁

门禁 通过标准 失败处理
正确性 Conclude Agent 的 root cause status、next step、证据引用和缺失信息必须与 evidence packet 一致。 保持 investigation active，要求工程师 revise 或让 Plan Agent 重新规划。
客户安全 不夸大 root cause，不把内部证据直接暴露给客户，不绕过工程师审批；工程师批准后必须再走现有 guardrail。 一票否决；回到 revise loop 或请求更多证据。
回归 历史高价值案例不能明显退化；关键场景必须稳定。 回到优化阶段，扩大评估样本。
版本治理 每轮 multi-agent run 都记录 plan_version、workflow_version、tool_policy_version、memory_index_version、guardrail_version 和 evidence_packet_version。 不得扩大线上流量。
文档治理 重复技术文档有 canonical/alias/archived 状态；相似但冲突的文档不会自动合并。 不得把该文档批次发布到主索引。
可回滚 multi-agent 主链路由 feature flag 控制，并可立即回退到现有 guardrail-only 行为。 不得上线。

十二、指标

工程师纠正率

需要工程师纠正 AI 结论的比例。目标是持续下降。

案例命中率

Case Memory Layer 检索到可用相似案例的比例。目标是随确认案例增加而上升。

证据充分率

AI 结论包含可追溯证据锚点的比例。目标是提升可审查性。

Conclusion 批准率

工程师无需 revise 即批准 conclusion 的比例。目标是随着 plan 和 memory review 质量提升而上升。

Revise 收敛轮数

从首次 conclusion 到工程师批准平均需要的 revise 轮数。目标是减少重复调查和无效问题。

客户安全失败率

内部证据泄露、root cause 夸大、未经批准生成客户回复的失败率。目标必须接近 0。

Guardrail 拦截率

工程师批准后被 Engineer Guardrail 拦截的比例。用于发现 conclusion 或客户草稿中的安全问题。

回滚次数

multi-agent 主链路因质量或安全问题回退到 guardrail-only 的次数。

文档重复率

技术文档主索引中 exact/near duplicate chunk 的比例。目标是持续下降。

Canonical 覆盖率

高频技术问题是否有明确 canonical topic 或 primary source。目标是持续上升。

十三、关键风险

风险 影响 缓解措施
自进化污染记忆 错误案例被反复召回，导致诊断偏移。 只有 confirmed 案例入 Case Memory Layer；保留 source_ticket_id 和 confidence；支持撤回或降权。
多 Agent 绕过安全节点 可能跳过审批或泄露内部证据。 Engineer approval、Engineer Guardrail、audit log 是不可跳过节点；orchestrator schema 必须强制执行。
Plan Agent 被 revise 指令误导 工程师 revise note 可能只描述局部错误，导致下一轮 plan 忽略原始证据。 每轮重新合并 ticket、handoff、上一轮 evidence 和 revise note；Conclude Agent 必须标注哪些结论来自证据，哪些来自工程师指令。
Case Memory Layer 与 Postgres 语义不一致 检索结果与权威工单状态冲突。 Postgres 为 source of truth；记忆层记录版本和 ticket id；检索结果必须回查权威状态。
把所有非官方知识放入记忆层 内部文档失去 citation、版本、source path 和检索可控性，engineer AI 难以解释证据来源。 按知识形态切分：文档型知识进 RAG non_official_only；案例、经验和偏好进 Case Memory Layer。
重复技术文档污染 RAG 相似 chunk 挤占 topK，降低证据多样性，也可能让旧版本覆盖新版本。 在 ingestion 前做 hash 去重和 near-duplicate clustering；retrieval 侧保留 family diversity 和 canonical boost。
相似但冲突的文档被误合并 会掩盖真实差异，导致 engineer AI 引用错误结论。 冲突文档必须进入 conflict review，禁止自动 canonical merge。
工具调用策略漂移 AI 调用错误工具或错误 fallback。 工具 allowlist、参数 schema 校验、调用 trace、失败回退到当前稳定策略。
Guardrail 被误当作调查 agent 会把现有 guardrail 扩展成不可审计的隐式调查逻辑。 Engineer Guardrail 只保留批准后的客户安全校验；调查必须由 Plan / Review / Implement / Conclude 链路完成并记录。

十四、后续建议

下一步不要推进 EvoAgentX，也不要把现有 guardrail 扩展成隐式调查 agent。先把线上 Engineer Multi-Agent 主链路做成可审计、可 revise、可回退的生产流程，并确保工程师批准后必须再走现有 guardrail。

建议的下一批实施任务是：multi-agent orchestrator、Plan Agent、Memory Review Agent、Implement Agent、Conclude Agent、engineer approve / revise loop、Engineer Guardrail 接入，以及基于 revise notes 的 replay eval。EvoAgentX 等线上闭环稳定后再重新评估。
